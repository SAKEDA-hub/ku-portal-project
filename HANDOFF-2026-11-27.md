## Что сделано

### Резервное копирование и хранение вложений

- Рабочая база на хосте находится в `~/ku-portal/data/db.json` (`/home/ku-portal/ku-portal/data/db.json`). Скрипт `deploy/backup-pull.sh` использует этот путь по умолчанию, поддерживает `KU_BACKUP_REMOTE_DIR`, проверяет обычный JSON и AES-GCM оболочку и сохраняет прежние копии при ошибке.
- Скрипт установлен как `~/.local/bin/ku-portal-backup`. 27 ноября была успешно создана настоящая копия в `/home/sakeda/Documents/KU-Portal/backups/2026-11-27` (около 2,4 МиБ). Данные и секреты в Git не добавлялись.
- SSH-копирование запускается с `-F /dev/null` и проверкой host key.
- Медиа экзамена сохраняются отдельными файлами `exam-media/<sha256>` с ограничением размера и ежедневными hard-link-снимками на 14 дней. Для KU Message используются отдельные файлы `uploads/<id>`; схема сообщений не менялась.

## Оставшиеся действия

1. Проверить в исходной пользовательской Linux-сессии наличие и запуск `ku-portal-backup.timer` (`systemctl --user list-timers --all`, затем журналы соответствующего сервиса). Если таймера нет, установить/включить его по локальной конфигурации и проверить запуск.
2. Просмотреть и слить PR #35 (портал), затем #2 в `ku-portal-desktop`, затем #2 в `ku-portal-project`. Перед слиянием учитывать, что изменения в `main` могут запустить существующий deploy/build workflow.
3. После слияния портала проверить сайт и логи deploy; после Desktop — результат GitHub Actions и появление Release с файлами; затем проверить ссылки скачивания в проекте.
4. Пакетную смену паролей применять отдельно только по согласованному списку пользователей и подготовленным новым паролям, после актуальной проверенной резервной копии. Проверить план и результат до передачи пакета в production.
