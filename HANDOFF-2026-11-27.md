## Что сделано

### Резервное копирование и хранение вложений

- Рабочая база на хосте находится в `~/ku-portal/data/db.json` (`/home/ku-portal/ku-portal/data/db.json`). Скрипт `deploy/backup-pull.sh` использует этот путь по умолчанию, поддерживает `KU_BACKUP_REMOTE_DIR`, проверяет обычный JSON и AES-GCM оболочку и сохраняет прежние копии при ошибке.
- Скрипт установлен как `~/.local/bin/ku-portal-backup`. 27 ноября была успешно создана настоящая копия в `/home/sakeda/Documents/KU-Portal/backups/2026-11-27` (около 2,4 МиБ). Данные и секреты в Git не добавлялись.
- SSH-копирование запускается с `-F /dev/null` и проверкой host key.
- Медиа экзамена сохраняются отдельными файлами `exam-media/<sha256>` с ограничением размера и ежедневными hard-link-снимками на 14 дней. Для KU Message используются отдельные файлы `uploads/<id>`; схема сообщений не менялась.

## Оставшиеся действия

1. Для production deploy задать в Settings → Secrets and variables → Actions значения `ALWAYSDATA_ACCOUNT`, `ALWAYSDATA_SSH_PASSWORD`, `ALWAYSDATA_API_TOKEN`, `ALWAYSDATA_SITE_ID` и переменную `ALWAYSDATA_KNOWN_HOSTS` с проверенным SSH host key. Затем повторно запустить workflow `Deploy` (`workflow_dispatch`) и убедиться, что `/api/version` возвращает новый commit.
2. Слить PR проекта [#2](https://github.com/SAKEDA-hub/ku-portal-project/pull/2) от форка `stikech/ku-portal-project` с правами сопровождающего. После этого проверить ссылки скачивания в `main`; Release `v1.0.16` уже опубликован.
3. В исходной пользовательской Linux-сессии `/home/sakeda` проверить `ku-portal-backup.timer` и его журналы (`systemctl --user list-timers --all`). Успешная разовая копия уже есть; ежедневное автоматическое срабатывание не подтверждено.
4. Пакетную смену паролей запускать отдельно только по согласованному списку пользователей и подготовленным новым паролям, после актуальной проверенной резервной копии. В production она пока не применялась.
