## Что сделано

### Ошибка резервной копии базы

- Пользователь подтвердил SSH-поиском, что рабочая база находится по адресу `~/ku-portal/data/db.json` (`/home/ku-portal/ku-portal/data/db.json`). Путь `ku-portal-mysql-new/KU-Portal/data` был неверным: это каталог кода, а не фактическая папка данных.
- В `ku-portal` скрипт `deploy/backup-pull.sh` теперь использует правильный путь по умолчанию, поддерживает `KU_BACKUP_REMOTE_DIR`, корректно проверяет обычный JSON и зашифрованную AES-GCM оболочку базы, а при ошибке сохраняет прежние копии.
- Скрипт установлен в `~/.local/bin/ku-portal-backup`. Успешно выполнена настоящая копия: `/home/sakeda/Documents/KU-Portal/backups/2026-11-27` (около 2,4 МиБ). Данные пользователей не выводились.
- В SSH используется `-F /dev/null` с обязательной проверкой host key: так исправляется влияние некорректного локального SSH-конфига, не отключая проверку сервера.
- Пользовательская systemd-служба и ежедневный таймер найдены; служба указывает на установленный скрипт. Запустить `systemctl --user` в рабочей среде агента не удалось из-за недоступной user bus, поэтому именно срабатывание таймера ещё надо подтвердить в пользовательской сессии.

### Хранение вложений

- В `ku-portal` медиа экзамена переносится из больших base64-строк `exam-sync.json` в файлы `exam-media/<sha256>`. Совпадающие файлы не дублируются, размер одного файла ограничен 25 МиБ, для удалённых медиа поддерживаются ежедневные hard-link-снимки на 14 дней. Старые клиенты, экспорт и экзамен получают прежний формат данных.
- Вложения KU Message уже хранятся отдельными файлами `uploads/<id>`, а в JSON остаются метаданные. Ограничения и проверка типов описаны в `docs/BACKEND.md`; существующую схему мессенджера в этой работе не меняли.
- Исправлены два тестовых сценария экзамена, которые не учитывали текущий вход через KU Portal и ограничения по назначенным группам. Оба теперь проходят отдельно.

## Проверки и известные проблемы

- Desktop: `node --test tests/*.test.js` — 11/11 проходят.
- Портал: точечные проверки резервного скрипта, файлов медиа, SSO и двух исправленных интеграционных сценариев проходят.
- Последний полный `npm test` портала: 68/74 проходят, 6 падают. Пять интеграционных тестов с теми же ожиданиями падали и на исходном `origin/main`; в основном их фикстуры расходятся с нынешними ограничениями по группам и входу в учебную базу. Не ослаблять серверную проверку доступа ради старых ожиданий тестов: обновить фикстуры и подтвердить правильное поведение.
- Отдельно не реализован `stageBundledRotations`, которого ожидает тест зашифрованной пакетной смены паролей. Этот сценарий затрагивает пароли пользователей, отзывает сеансы и очищает старые копии базы. Не внедрять и не запускать его, пока пользователь явно не разрешит именно пакетную смену учётных данных. Наличие теста не является разрешением.
- Сборку Android локально не запускали: в среде нет JDK. Платформенные релизы Desktop создаются GitHub workflow только после прохождения проверок на `main`. На момент проверки опубликованного Desktop Release не было, поэтому ссылки проекта станут рабочими после успешной публикации релиза.
